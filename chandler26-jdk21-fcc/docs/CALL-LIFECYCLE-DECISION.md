# 通话结束、坐席参与与日终对账决策

## 1. 状态与结论

评估日期：2026-10-04。本文记录设计方向、当前工作区实现及已知偏差，不代表部署或完整真实话务验收通过。架构入口见 [Java 控制面设计](DESIGN.md)，交付状态与优先级仍由 [交付计划](../../docs/fcc-delivery-plan.md) 维护。

结论：坐席服务应能独立于客户 Call 结束，但不能将“任意一个坐席 Leg 结束”无条件等同“坐席立即示闲”。`call-center-backend` 仅作为成熟业务语义参考，不复制旧表结构、协议、监听器分支或当前/历史双表。

## 2. 生命周期边界

| 对象 | 表达的事实 | 结束的含义 |
| --- | --- | --- |
| Call | 一次稳定 `call_id` 的业务通话聚合 | 业务流程结束；不是某个坐席话道的别名 |
| Leg | 一个由 `node_id + channel_uuid` 定位的真实话道 | 这个话道结束，不自动代表其他话道或整个 Call 结束 |
| 坐席参与 | 某坐席在 Call 中的一段服务及其有效话道关联 | 该段服务结束，可以解除对应占用，不影响其他坐席 |

`fcc_agent_service_session` 已存在于基线 DDL，但当前没有完整参与记录写入与状态推进链路，不能把表存在当成能力已完成。后续应基于现有事实模型补齐参与关系，不新建语义重复的当前/历史通话表。

普通两方通话通常只有一个坐席服务 Leg，该 Leg 结束可结束坐席参与；客户仍可继续评价、IVR 或结束语音。咨询、三方、转接和话道替换可能出现多个关联 Leg，必须判断该坐席是否仍有有效服务参与。不能仅按工号、Call 主坐席字段或单个旧 Leg 推断占用已结束。

## 3. 坐席释放规则与 ACW 边界

设计要求如下，尚未全部实现：

1. 结束事件先落盘，并通过精确身份关联 Leg 与坐席参与；未知关联保持待对账，不关联“最新通话”。
2. 结束的是对应参与；只在该坐席没有其他有效参与或服务话道时解除占用。转接前后的参与不能相互误释放。
3. 释放使用原参与、原 Call 和当前占用的条件更新。旧 Call 的迟到事件不能释放新 Call；同 Call 内的话道替换也必须受参与身份约束，仅比较 `active_call_id` 不够。
4. 重复结束事件不重复释放、计费、创建回拨或发送新的副作用命令；迟到振铃、应答事件不复活终态参与。
5. 挂机请求或同步 `ACCEPTED` 不等于 Leg 已结束。发送对端 Hangup 后，不能仅因命令已受理就将对端坐席视为可接单。

产品已确认不强制话后整理：参与结束后立即按登录状态恢复 `LOGIN -> READY`、`LOGIN_BUSY -> BUSY`、`LOGOUT -> UNREADY`。这是恢复原示闲/示忙意图，不是所有挂机统一示闲。挂断请求受理仍不能提前释放。

客户端不再进入强制 ACW，不倒计时、不自动提交小结；旧小结使用结束通话的独立快照，提交不能释放或清除较新的通话。新来电自动收起小结抽屉，待填入口保留。未提交的小结队列仅在内存中，刷新或退出登录会丢失；尚无持久草稿功能。后端仍仅允许本人主坐席且整个 Call 已结束时保存，客户评价未结束时可能需稍后重试；多参与者小结授权尚未扩展。

## 4. Call 收尾与日终对账

实时结束事实是正常收尾路径，日终任务只修复漏事件、重启或处理中断留下的残留，不替代实时坐席释放。单个坐席参与结束时，客户评价、其他坐席服务及 Call 不应被连带结束。

当前工作区 `ExpiredCallReconciliationJob` 使用以下默认配置：

| 环境变量 | 默认值 | 含义 |
| --- | --- | --- |
| `FCC_CALL_CLEANUP_ENABLED` | `true` | 启用日终对账 |
| `FCC_CALL_CLEANUP_CRON` | `0 0 1 * * *` | 每日 01:00 执行 |
| `FCC_CALL_CLEANUP_TIMEZONE` | `Asia/Shanghai` | 调度时区；事实时间仍使用 UTC |
| `FCC_CALL_CLEANUP_EXPIRE_HOURS` | `24` | 按 Call 开始时间选择候选，不是强制挂机时限 |
| `FCC_CALL_CLEANUP_PAGE_SIZE` | `100` | 每页候选数，当前限制 1–500 |

对账原则：

- 时间过期只触发检查，不构成结束证据。活跃长通话不能因到达 01:00 被终止。
- 已持久化终态可用于修复关联残留；或依据全部已知话道的真实结束事实判断 Call 已结束。身份不全时不能假定已覆盖全部话道。
- 缺失结束事实时，只有覆盖相关所属节点的可靠完整快照才能证明已知话道不存在。多节点聚合尚未验收；单节点结果不能证明其他节点话道已不存在。
- 超时、无响应、断网、节点心跳失联、畸形或不完整结果都不能当作空快照。证据不足延后对账。
- 快照确认不存在但真实结束时间或原因未知时，明确记录 `RECOVERY_UNKNOWN` 与修复依据；不能伪造正常挂机、精确计费时长、录音完成或业务成功。
- 快照查询在数据库事务外进行，提交前检查版本。并发事件更新导致版本冲突时跳过或重试；事实提交后再清理可重建缓存。
- 收尾保持幂等，并记录证据、时间和关联标识。自动外呼未知结果不能因兜底被误判成功或触发盲目重拨。

## 5. 当前实现与已知偏差

| 边界 | 当前工作区行为 | 仍需补齐 |
| --- | --- | --- |
| 真实 Leg 结束 | `CallFinalizationService.recordChannelEnd` 先锁 Call 行，保存源 `DESTROY`，调用 `AgentLegLifecycleService`；串行化同 Call 的并发结束 | 持久参与记录及新 Leg 创建/替换的统一并发边界 |
| 按 Leg 释放 | `releaseEndedLeg` 关联坐席与结束 Leg，并约束原 `active_call_id`；共享 SQL 排除同坐席其他活跃 AGENT Leg | 参与级身份与状态完整写入；真实话道替换验收 |
| Call 终态收尾 | `releaseAgents` 和普通 `release` 复用相同活跃 Leg 检查，不仅凭 Call 终态释放 | 统一恢复通知补偿，验证全部释放入口 |
| 客户评价 | 呼入/外呼存在坐席先挂机后启动客户评价的路径 | 参与释放不终止评价，评价完成不释放坐席后续新通话 |
| 客户端 | 关联当前 callId 的结束/参与释放使媒体态回到 IDLE；普通 READY/BUSY 通知不清理通话；小结独立排队，保存不改坐席状态 | 重连与 SIP/WebSocket 顺序真实联调、持久草稿 |
| 日终修复 | 已有分页候选、结束证据判断、版本校验和批量关联收尾代码 | 多节点完整性、快照与运行事件竞争、通知补偿及部署环境恢复验收 |

## 6. 备选方案与取舍

共享释放查询使用 `fcc_call_leg(call_id, role_type)` 索引限定同 Call 的 AGENT Leg，再检查 metadata 工号或现有 service-session 关联；归属不明的活跃 Leg 保守阻止释放。后续可靠性整改增加普通 AGENT Leg 的参与同步、版本列和 `leg_id` 唯一键，Leg 写入与源 END 共用 Call 锁，新增写成本和升级顺序见 [运行可靠性整改](RUNTIME-RELIABILITY.md)。转接目标、历史参与与角色仍未完整打通；尚未在 MySQL 8 执行和验证执行计划。

- **等整个 Call 结束才释放坐席**：实现简单，但评价或另一坐席继续服务会无意义延长原坐席占用，不采用作为统一规则。
- **任意坐席 Leg 结束立即示闲**：普通两方场景可行，但多 Leg、话道替换、示忙/退出和 ACW 场景不成立，不采用作为统一规则。
- **以坐席参与为释放边界**：采用此方向。增加参与关系与状态管理成本，但能够表达转接、咨询和三方，也能隔离原坐席与客户后续流程。

## 7. 后续实施与验收条件

以下是本优化的缺口与验收条件，不是新增交付优先级清单：

- 补齐现有坐席参与事实，明确参与和 Leg 的关联、结束条件、替换关系及占用条件更新；统一实时与兜底释放策略。
- 已确定立即恢复示闲/示忙、可选小结；继续验收客户端操作和后端状态一致性，小结不能清理新通话。
- 客户端已有迟到示闲隔离保护；继续覆盖 WebSocket 与 SIP 结束通知先后顺序、READY 先到、重复与重连的真实链路。
- 验收普通两方、坐席先挂后客户评价、客户先挂后坐席 Leg 延迟结束、转接、咨询失败、三方单人退出及同坐席话道替换。
- 验收旧 Call 结束到达时坐席已接新 Call、同 Call 旧 Leg 迟到结束、重复/乱序事件和版本冲突；不得误释放当前服务。
- 验收服务重启、漏结束事件、快照超时/无响应/不完整、节点失联、长通话跨日和日终重复执行；证据不足不得强制结束。
- 核对 Call、Leg、参与、Bridge、Flow、自动外呼结果与录音事实；未知录音不能被标为已完成，未知业务结果不能盲重试。

当前仅有部分策略、幂等与隔离 SQL 的自动化验证；该 SQL 验证环境为临时 MySQL 9.7，不能替代要求的 MySQL 8 验证。完整 FreeSWITCH/NATS/媒体、客户端竞态和多节点恢复尚无本优化的端到端验收证据。用户已确认 `0000` 绑定、呼入、呼出和自动外呼基础测试通过，这不等于本次异常恢复与多参与释放测试通过。
