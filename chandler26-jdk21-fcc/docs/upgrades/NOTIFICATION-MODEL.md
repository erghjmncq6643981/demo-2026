2. 发布修正后的 Java 资源。全新安装使用更新后的 `docs/fcc-schema.sql`，无需 V2 修复脚本。**已有数据库不能通过重跑基线升级**，避免重置生效版本指针。
3. 对仍使用原错误 V1 的存量数据库，审核后执行 [目录 V2 升级 SQL](2026-10-04-notification-model-v2.sql)。脚本锁主定义行，追加 V2 草稿、归档 V1、发布 V2、最后切换指针；内容和旧 checksum 不匹配时不强制覆盖。禁止 `mysql --force`；任何错误立即停止并回滚，不继续提交。
4. 检查当前版本为 2、checksum 与资源一致且仅一个 PUBLISHED；通过已有受保护的流程重载能力刷新每个运行实例的 `SYSTEM_NOTIFICATION` 缓存，并验证新建通话的固定版本。仅等待缓存自然刷新不算上线完成。

旧版本 JSON、正在运行和历史通话的固定快照均保持原样。V1 与 V2 表达的是相同固定运行能力，仅目录分支描述不同；旧快照不会被追溯修正。没有匹配旧 V1、已经是其他版本或 V2 被其他内容占用时，必须人工核对，不自动回填。

## 索引、修复与验证边界

不增加索引；沿用主键、`(flow_definition_id, version_no)` 唯一索引和 `published_marker` 单一发布约束。每个受影响的系统定义只追加一行，发布状态切换产生少量唯一索引写入，不扫描或更新高量通话事实。

如需回退，在同一事务锁定主定义并核对当前 V2 和两份 checksum：先归档 V2，恢复原 V1 的 PUBLISHED，最后将指针恢复为 1；保留 V2、历史引用与快照，不删除版本。完成后逐实例重载缓存。内容被意外修改或其他版本已发布时禁止盲目回退。
