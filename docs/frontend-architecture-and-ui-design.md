# FCC 前端架构与工程治理

## 1. 文档范围

本文记录 FCC 三个前端的当前运行边界和工程准入要求：

| 工程 | 用户 | 默认端口 | 后端 |
| --- | --- | --- | --- |
| `chandler26-fcc-admin-web` | 管理员、运营、班组长 | `8000` | `fcc-admin :8089` |
| `chandler26-fcc-client-web` | 坐席、班组长 | `8888` | `fcc-admin :8089`、`fcc-server :8085`、FreeSWITCH SIP WebSocket |
| `cloud-2025/fswitch-web` | 通信工程师、平台运维 | `8008` | Go Sidecar `:8088` |

本文不把原型、规划或静态演示描述成已交付能力。页面是否可用以真实 API、状态处理和可重复验证为准。

产品能力和验收优先级见 [产品设计总览](fcc-product-design.md)；已确认的前后端参数、状态和能力差异见 [契约检查](fcc-contract-alignment.md)。下文“接入”仅指存在代码入口，不代表真实环境已验证。

## 2. 运行架构

```text
fcc-admin-web :8000 ----------------------> fcc-admin :8089
                                                     |
                                                     +--> MySQL / Redis
                                                     +--> Sidecar :8088 (管理面)

fcc-client-web :8888 -- /api/admin ------> fcc-admin :8089
                    +-- /api/telephony --> fcc-server :8085
                    +-- /ws/agent -------> fcc-server :8085
                    +-- SIP WS/WSS ------> FreeSWITCH :5066/:7443

fswitch-web :8008 -- /api/v1 + WS -------> Sidecar :8088
                                                     |
                                                     +--> NATS
                                                     +--> ESL :8021
                                                     +--> PostgreSQL
```

边界要求：

- 管理端不直接调用 NATS、ESL 或 FreeSWITCH。
- 坐席端的管理 REST、话务 REST、业务 WebSocket、SIP/WebRTC 是四个明确适配器，不能合并为一个“连接成功”状态。
- 运维端只管理 Sidecar/FreeSWITCH，不承载坐席、客户、技能组和业务路由逻辑。
- Java 控制面只通过 NATS/FCC 调用 Sidecar，不建立 ESL 连接。

## 3. 当前实现

坐席端已有复用 Vue 的 Electron 测试外壳，首批使用实体话机承载语音；桌面外壳负责托盘、单实例、原生通知、窗口恢复及展示回执。fcc-server 负责客户资料与弹屏收件人、内容、生命周期、补发规则。外壳通过受限 DesktopBridge/IPC 接入本机能力，禁用页面 Node 集成并启用上下文隔离。当前包未签名，真实 Windows 的锁屏、专注助手、断线重连和窗口激活仍需验收，不能把生成测试包表述为正式客户端交付。

### 3.1 管理端

当前代码已经接入：

- 管理员登录、当前用户与 Sa-Token 请求头。
- 坐席、终端绑定、客服组、组员与组织报表。
- 分机列表、创建、删除和 IVR 绑定。
- CDR 列表、统计、详情、录音播放及下载。
- 回拨任务查询、指派和呼叫。
- 分页流程/版本摘要、固定阶段画布、参数编辑、草稿保存、发布和真实执行轨迹；旧仿真入口已删除。
- 运行监控和部分资源/客户端管理界面。

### 3.2 坐席端

当前代码已经接入：

- 坐席登录、接听终端加载和切换。
- `/ws/agent` 心跳、消息分发和定时重连。
- JsSIP 注册、来电、外呼、接听、挂机、静音、DTMF 与远端音频播放。
- 话务 REST 入口：外呼、挂机、保持、DTMF、转接。控制请求与最终状态已区分；班长干预尚未实现，入口禁用、接口明确拒绝。
- 来电弹屏、通话工作区、ACW、回拨任务、CDR 和坐席监控。

### 3.3 FreeSWITCH 运维端

当前代码已经接入：

- 节点状态、注册表、分机、Sofia Profile 和网关。
- 活跃 Channel/Call、强拆和转接。
- FreeSWITCH 原始 CDR。
- CLI 执行和控制台日志 WebSocket；Sidecar 原生授权与审计不完整，限制访问需依赖部署边界。

## 4. 工程结构准入

三个前端都采用“领域拥有完整切片”的目标结构：

```text
src/
  features/
    <domain>/
      api/
      components/
      composables-or-store/
      models/
      tests/
  shared/
    api/
    ui/
    feedback/
    formatting/
  App.vue
```

规则：

- 领域拥有 UI、API 适配、状态、纯模型和测试。
- `App.vue` 与 Layout 只负责外壳和装配。
- 跨领域流程进入显式 coordinator/use case，不由页面组件串联多个后端。
- 新流程中的组件不直接调用 Axios；组件触发领域动作，由领域动作处理 pending、错误、重试和最终状态对账。
- 600 行进入强制设计评审，1000 行以上禁止继续堆叠功能。
- 列表只承载紧凑摘要；Leg、执行轨迹、流程 JSON、录音元数据等按详情接口加载。
- Java `Long`、Snowflake ID、Call ID、Channel UUID、Ctrl ID、Recording ID 全部按不透明字符串处理。

## 5. 状态与实时通信

### 5.1 通用数据状态

所有查询必须覆盖：

- 首次加载；
- 空结果；
- 请求失败与可执行重试；
- 认证失效或无权限；
- 使用上次数据时的 stale 标识；
- 条件变化后的取消或过期响应。

所有写操作必须覆盖：

- 输入校验；
- 提交中防重复；
- 后端业务失败；
- 网络未知结果；
- 成功反馈及数据刷新；
- 影响服务或删除数据时的二次确认。

### 5.2 坐席呼叫状态

呼叫业务状态、命令状态、业务 WebSocket 状态和 SIP 媒体状态分别建模。REST 返回成功只表示命令已受理，不能直接视为接通、转接或挂机完成。

状态变化必须满足：

- 终态幂等；
- 重复事件不重复进入 ACW；
- 延迟的 `RINGING` 不覆盖 `CONNECTED` 或终态；
- 重连不创建第二个心跳、SIP UA 或事件订阅；
- 登出、卸载和终端切换清理全部定时器、监听器、MediaStream 和 Session；
- 麦克风拒绝、注册失败、媒体失败、远端挂机和业务 WebSocket 断线分别可见。

### 5.3 运维刷新状态

轮询和 WebSocket 由统一状态层管理，记录最近成功时间。刷新失败时只能：

- 保留上次数据并明确标记 stale；或
- 清空并显示不可用。

不得吞掉错误后继续展示伪造的 HEALTHY、在线数、版本号或容量值。

## 6. 交互与视觉

- 这是高频操作工具，界面以扫描、比较和重复操作为中心，不使用营销式 Hero、装饰性大卡片或虚假实时动效。
- 页面标题、表格、筛选和操作保持稳定层级；固定操作区不得因动态内容发生跳动。
- 破坏性操作、流程发布、强拆、强制注销、删除分机和原生命令必须使用应用内确认与结果反馈。
- 长号码、UUID、URL、错误信息和中文业务名称不得覆盖相邻内容；使用换行、截断加完整值提示或详情区。
- 录音、电话号码、客户信息和协议原文按权限展示，禁止写入前端日志或静态演示数据。
- 模拟、占位和不可用指标必须显式标注，不得表现为生产实时值。

## 7. 当前技术债基线

2026-09-19 治理后的源码状态与剩余边界：

| 工程 | 当前问题 |
| --- | --- |
| 管理端 | 分机已拆分 extensions/settings/fleet；流程改为真实定义编辑器；CDR、组管理状态已提取到各自 composable，映射与树模型独立 |
| 管理端 | CDR 和组管理视图仍超过 600 行，后续按列表/详情继续拆分；权限、发布失败与录音浏览器回归尚不完整 |
| 坐席端 | 运行配置与呼叫状态模型已提取，重复/乱序事件及重连有测试；真实 SIP 和双向音频仍需联调 |
| 运维端 | 顺序轮询和定时器清理已加入，失败显示 stale/不可用；分机视图仍超过 600 行，部分操作仍用原生确认框 |
| 自动化 | 管理端 4 个纯模型测试、坐席端 10 个测试通过；三端构建通过，不能替代真实接口及浏览器回归 |
| 构建产物 | 管理端/坐席端生成的 Vite JavaScript、声明文件和 `*.tsbuildinfo` 从源码移除并忽略 |

运维端离线浏览器检查覆盖了失败提示和禁用操作；登录后的管理端、移动敏感宽度和完整媒体链路尚未完成验证。

## 8. 验证要求

每次前端交付至少执行：

```bash
npm run build
git diff --check
```

还必须：

- 对变更模块执行 ID 数值转换扫描；
- 在浏览器验证桌面与移动敏感宽度；
- 验证加载、空、失败、重试、无权限和长文本；
- 实时通信变更验证断线、重连、重复事件、乱序事件和资源清理；
- 媒体变更验证权限拒绝、注册失败、来去电、双方挂机与自动播放限制；
- 无法连接真实 MySQL、Redis、NATS、Sidecar、FreeSWITCH 或 SIP 终端时，明确记录未验证边界。
