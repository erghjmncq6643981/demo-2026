# AI 开发规则

本文档是宝贝激励助手的 AI 协作规则。后端、前端、数据库、设计文档、启动脚本都应遵守本文档。

## 项目边界

- 后端项目：`/Users/chandler/Documents/repository/github/demo-2026/chandler26-jdk17-motivation`
- 前端项目：`/Users/chandler/Documents/repository/github/demo-2026/chandler26-jdk17-motivation-web`
- 两个项目按一个前后端分离产品维护，任何接口、字段、SQL、DTO 或 UI 状态变化都要联动检查。
- 产品设计源文档放在后端项目 `docs/` 下。

## 产品语义

- 产品名称是“宝贝激励助手”。
- 可见文案优先使用“宝贝”，避免继续扩大“孩子”文案。
- 家长侧负责管理规则、审核、奖励履约、配置和日志追踪。
- 宝贝侧负责查看、打卡、兑换、关注奖励状态和确认礼物券。
- 任务日历、奖励日历、货币流水、礼物兑换券、宝贝成长日志、用户偏好配置都是核心产品面，不是临时演示数据。

## 后端规则

- 使用 Spring Boot、MyBatis-Plus、MySQL、Spring Security、JWT。
- Controller 保持薄层，业务逻辑放在 Service。
- API 入参和出参使用 DTO；列表、详情、保存、状态流转接口要保持显式。
- 异常使用项目专属运行时异常，异常描述要能被业务人员理解。
- 状态、类型、来源等业务值使用枚举或集中常量，避免魔法值散落。
- 业务日志使用 info 级别，格式要能看出“什么人什么时间做了什么”。
- 系统诊断日志使用 debug 级别。
- 重要操作写入 `motivation_system_log`，包括任务打卡/审核、奖励兑换/审核/履约、货币变化、账号与宝贝档案关键操作、偏好配置变更。
- 家长/监护人/宝贝账号的权限在 Service 校验，不能只靠前端隐藏按钮。

## 数据持久化规则

- 不能把核心业务状态只存在浏览器里。
- 以下数据必须落库：当前观察宝贝、任务/奖励日历视图偏好、任务记录、货币余额、货币流水、奖励兑换券、奖励履约状态、宝贝成长日志、操作日志、头像压缩数据。
- 用户习惯类配置使用用户偏好表保存；离线或后端不可用时可用 localStorage 兜底，但不能作为在线主存储。
- 积分/货币余额只能通过流水驱动，不能绕过 `motivation_point_ledger` 直接修改。
- 奖励兑换在申请时就要校验可用余额，并考虑审批中的占用；拒绝后要释放占用或返还。

## 数据库规则

- SQL 放在 `src/main/resources/db/init`。
- `000_motivation_all_in_one_mysql.sql` 用于新库一次性准备。
- 已执行过的环境使用新增编号补丁 SQL，不悄悄修改已经执行过的迁移意图。
- 表和字段必须有清晰中文注释。
- 用户、宝贝、任务、日历、任务记录、货币流水、奖励兑换、奖励履约、偏好配置等高频查询需要索引。
- 修改持久化结构时，同步检查 SQL、实体、Mapper、DTO、Service 映射和前端 API 字段。

## 前端规则

- 功能代码放在 `public/src/features/**`。
- 共享工具放在 `public/src/shared/**`。
- `public/app.js` 只做入口、状态编排和事件连接；新的大块业务逻辑要逐步模块化。
- API 调用集中在 `public/src/shared/api.js`。
- 状态文案、图标、枚举展示尽量集中在 shared text/helper 中。
- 破坏性操作、扣分、删除、拒绝、撤销等动作必须二次确认。
- 新增/修改使用弹窗；删除使用二次确认。
- 管理列表默认只保留关键字搜索，次要筛选放到更多条件中。
- 修改 UI 后检查桌面和移动端，尤其是侧边栏、弹窗、日历、表格操作列、按钮换行和长文本截断。

## 日历规则

- 任务日历只展示任务和货币流水，不再承载奖励业务操作。
- 奖励日历专门展示奖励兑换、购买、运输、日程实现和宝贝确认。
- 月视图/周视图是用户习惯，需要按操作者保存。
- 今日按钮、今日高亮、日期大小和颜色属于日历体验配置。
- 日期格子要有最小可用宽度，任务名在格子内保持短显示，避免遮挡日期。
- 家长可以在任务日历日期弹窗快速新增当日任务和给任务打卡；宝贝只能按权限打卡。

## 任务规则

- 任务类型为每日、每周、每月。
- 每日任务支持点选小时块；每周任务支持点选周一到周日；每月任务支持点选日期。
- 完成次数最低为 1，不能超过可选时间块/日期数量。
- 任务有色彩、说明、奖励类型、奖励数量、积分生效方式。
- 打卡弹窗中的奖励图标默认全部高亮，允许减少或增加实际奖励数量，但必须符合后端校验。
- 宝贝侧打卡需要家长审批时，要在家长侧形成待确认任务。

## 奖励规则

- 奖励有主流程：申请兑换 -> 家长确认/拒绝 -> 履约中 -> 宝贝确认。
- 奖励实现方式决定分支流程：
  - 库存扣减/家长执行：家长确认后可完成，宝贝最终确认。
  - 家长购买：家长确认 -> 已下单 -> 运输中（预计到达时间）-> 已到货 -> 宝贝确认。
  - 家长实现：家长确认 -> 加入日程（开始/结束时间）-> 进行中 -> 已实现 -> 宝贝确认。
- 奖励日历由家长维护状态，宝贝只查看状态和确认礼物券。
- 宝贝礼物兑换券需要分为未使用和已使用，点击后展示奖励信息和礼物动态。
- 奖励商店兑换弹窗必须清晰展示所需消耗、当前余额、是否可用更高币值支付和找零。

## 货币规则

- 货币类型展示为 1 级、2 级、3 级，对应默认星星、红花、皇冠。
- 1 级币值必须小于 2 级，2 级币值必须小于 3 级。
- 货币图标、颜色、比例可以配置。
- UI 中儿童侧优先使用图标和数量，减少依赖文字理解。

## AI 功能规则

- AI 可以生成任务建议、奖励建议和家庭激励方案。
- AI 生成内容必须先进入草稿或建议状态，不能自动生效。
- 家长确认后，AI 建议才可以变成正式任务、规则或奖励。
- AI 生成的规则需要结构化保存，便于前端编辑和后端验证。
- AI 不得自动修改余额、任务生效规则、奖励库存、奖励履约状态。

## 启动脚本规则

- 启动、停止、重启脚本放在后端项目 `scripts/`。
- 启动脚本要确认前后端应用已可访问后再返回。
- 停止和重启脚本也要确认前后端进程退出后再返回。
- PID、日志、运行状态文件放在 `.runtime/`。

## 验证要求

- Java 修改后至少运行 `mvn -q -DskipTests compile`。
- JS 修改后至少运行 `node --check`。
- UI 或交互修改后使用浏览器验证。
- SQL 修改后检查语法、注释、索引和实体字段一致性。
- 角色权限相关改动要验证家长账号和宝贝账号。
- 数据持久化相关改动要验证刷新、重新登录、后端重启后的状态恢复。
